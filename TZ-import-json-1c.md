# ТЗ: внешняя обработка загрузки номенклатуры Smart Tender из JSON

## 1. Цель

Внешняя обработка 1С, которая по файлу JSON (выгрузка отмеченных позиций KSM из веб-каталога Smart Tender) для **выбранной оператором категории номенклатуры**:

1. обеспечивает наличие фасетов (доп. реквизитов) и их значений в этой категории;
2. создаёт элементы **Номенклатура (Smart Tender)**;
3. привязывает их к **уже существующей обычной номенклатуре** (по коду 1С из JSON), если она найдена;
4. заполняет **Наименование** и **Полное наименование** склейкой значений фасетов.

`kmat` в карточку ST **не** сохраняем — достаточно фасетов, категории, привязки к обычной номенклатуре и двух наименований.

---

## 2. Источник данных

### 2.1. Откуда берётся файл

В веб-каталоге проекта отмечают позиции KSM → «Зберегти» → JSON  
(имя вида `ksm-selected-YYYYMMDD-HHMM.json`).

В обработку загружается **именно этот** файл. Содержимое файла = полный список к загрузке (включая позиции со статусом «скасована»). Фильтрацию по статусу **не** делать.

### 2.2. Формат JSON

Корневой элемент — **массив** объектов. Пример одной позиции:

```json
[
  {
    "status": "активна",
    "name": "Блістер круглий з логотипом ТАРТА, d-210 мм, h-78.5 мм, …",
    "group": "…",
    "group_code": "P1…",
    "category": "…",
    "category_code": "P1",
    "int_code": "ПАТ00031",
    "kmat": "P1…………",
    "unit": "шт.",
    "facets": [
      {
        "code": "P1xx",
        "name": "Тип блістера",
        "value": "Блістер круглий з логотипом ТАРТА",
        "value_code": "1"
      },
      {
        "code": "P1yy",
        "name": "Розмір блістера",
        "value": "d-210 мм, h-78,5 мм",
        "value_code": "2"
      }
    ]
  }
]
```

| Поле JSON | Назначение для загрузки |
|-----------|-------------------------|
| `int_code` | Код **обычной** номенклатуры 1С для поиска и привязки |
| `unit` | Единица измерения (поиск по наименованию) |
| `facets[]` | Фасеты позиции; **порядок элементов массива** = порядок для склейки имени (в файле `position` не пишется, массив уже отсортирован при экспорте) |
| `facets[].name` | Имя доп. реквизита (фасета) в категории |
| `facets[].value` | Значение фасета |
| `facets[].code`, `value_code` | Справочно; для поиска в 1С **не** использовать |
| `status`, `name`, `group*`, `category*`, `kmat` | В карточку ST не пишутся (могут попасть в лог при ошибке) |

## 3. UI внешней обработки

Две вкладки.

### 3.1. Вкладка «Загрузка»

| Элемент | Описание |
|---------|----------|
| Файл JSON | Выбор файла на диске |
| Категория номенклатуры | Выбор существующей категории 1С (как «Блістери круглі»), в которую грузим |
| Кнопка «Загрузить» | Запуск алгоритма |
| Краткая сводка | Числа: создано фасетов / значений / ST; не найдена обычная номенклатура; ошибок по позициям |

### 3.2. Вкладка «Лог»

Табличный лог по ходу загрузки и по ошибкам.

Минимум колонок:

- дата/время;
- `kmat` (из JSON);
- `int_code`;
- этап (`Фасет` / `Значение` / `ЕИ` / `Привязка` / `Создание ST` / `Позиция`);
- результат (`OK` / `Пропуск` / `Ошибка`);
- сообщение / причина;
- при ошибке позиции — **дамп данных позиции** (JSON строки или ключевые поля + список фасетов), чтобы можно было разобрать без исходного файла.

При ошибке по позиции: изменения **этой** позиции откатить; остальные позиции продолжать. Детали — в лог.

## 4. Объекты 1С *(уточнить по конфигурации)*

Имена метаданных в ТЗ намеренно не фиксируются. Программист сверяет по конфигурации и скринам:

| Смысл | Как выглядит у пользователя | Уточнить в конфигурации |
|-------|-----------------------------|-------------------------|
| Категория | «Категории номенклатуры», вкладка «Дополнительные реквизиты» / «Фасеты» | Имя справочника/объекта категории, связь с набором свойств |
| Фасет | Доп. реквизит категории, представление фасета (напр. «Матеріал блістера») | Как создать доп. реквизит, привязать к категории, тип значения «Дополнительное значение» |
| Значение фасета | Список значений доп. реквизита (напр. «ПЕТ+ПЕ прозорий, 650 мкм») | Справочник доп. значений, владелец = реквизит |
| Номенклатура (Smart Tender) | Список/карточка «Номенклатура (Smart Tender)»: наименование, полное, номенклатура, категория, ЕИ, «Действует», таблица «Фасеты» | Имя справочника ST, реквизиты, как пишутся значения фасетов в элемент |
| Обычная номенклатура | Поле «Номенклатура» в карточке ST; код вида `ПАТ00031` — штатная нумерация **базовой** номенклатуры | Имя справочника, реквизит кода для поиска по `int_code` |
| Единица измерения | «шт.» и т.п. | Справочник ЕИ, поиск по наименованию |

**Важно:** у Smart Tender **отдельный «бизнес-код» из JSON не задаём**. Код вида `ПАТ00031` относится к обычной номенклатуре 1С. Если у справочника ST есть служебный код — оставить штатную автонумерацию платформы/конфигурации, из JSON его не заполнять.

## 5. Алгоритм загрузки

Вход: путь к JSON + выбранная категория.

1. Прочитать JSON (массив). Пустой/битый файл → ошибка в лог, выход.
2. Для **каждой** позиции массива — в **отдельной транзакции** (или эквивалент «откат только этой позиции»):

### 5.1. Подготовка фасетов позиции

Для каждого элемента `facets[]` **по порядку массива**:

1. Если `value` пустой (после `Trim`) → **пропустить весь этот фасет** (не создавать реквизит «ради пустого», не участвует в имени). Запись в лог: `Пропуск`, причина «пустое value».
2. Найти в **выбранной категории** доп. реквизит (фасет) **по имени** = `facets[].name` (сравнение без учёта лишних пробелов по краям; регистр — как принято в конфигурации для доп. реквизитов; по умолчанию — точное совпадение имени после Trim).
3. Если фасета нет → **создать** доп. реквизит с этим именем, тип значения — «Дополнительное значение» (как в UI категории), **добавить в конец** списка фасетов категории. В лог: создан фасет.
4. В списке значений этого фасета найти значение по правилам п. 6.
5. Если значения нет → **создать** значение с текстом из JSON `value` (как в файле). В лог: создано значение.
6. Запомнить пару (фасет, значение) для этой позиции — для записи в ST и для склейки имени.

Если на шагах создания фасета/значения/чтения категории ошибка → откат позиции, лог с причиной и данными позиции, переход к следующей.

### 5.2. Единица измерения

- Взять `unit` из JSON.
- Найти ЕИ в 1С **по наименованию**.
- Не найдена → оставить в ST **пустую** ссылку, в лог `Пропуск`/предупреждение «ЕИ не найдена: …».
- Не создавать новую ЕИ.

### 5.3. Привязка к обычной номенклатуре

- Если `int_code` заполнен → найти обычную номенклатуру **по коду 1С**.
- Найдена → записать ссылку в поле «Номенклатура» карточки ST.
- Не найдена или `int_code` пуст → поле «Номенклатура» оставить пустым, загрузку позиции **не** считать ошибкой. В лог: «обычная номенклатура не найдена» / «код пуст».

### 5.4. Создание номенклатуры Smart Tender

**Дубликаты ST не ищем — всегда создаём новый элемент.**

Заполнить:

| Поле ST | Значение |
|---------|----------|
| Категория номенклатуры | Выбранная в обработке категория |
| Единица измерения | Найденная ЕИ или пусто |
| Номенклатура | Найденная обычная или пусто |
| Действует | Да (или штатное значение конфигурации для нового элемента) |
| Фасеты | Набор значений, собранный в п. 5.1 (способ записи — по API конфигурации) |
| Наименование | Склейка значений фасетов (п. 5.5) |
| Полное наименование | Та же строка, что и Наименование |

Записать элемент. Успех → лог `OK`. Ошибка записи → откат позиции + лог.

### 5.5. Склейка наименования

- Берутся **только** фасеты, прошедшие п. 5.1 (с непустым `value`).
- Порядок — **порядок в массиве `facets` JSON** (не порядок списка фасетов в категории 1С).
- Текст каждого куска — значение фасета (`value`); при склейке использовать уже сопоставленное/созданное значение в 1С (его представление должно совпадать с `value`, с учётом нормализации только при **поиске**).
- Разделитель: `", "` (запятая + пробел).
- Пример:  
  `Блістер круглий з логотипом ТАРТА, d-210 мм, h-78,5 мм, ПЕТ+ПЕ прозорий, 650 мкм, …`

Поле `name` из JSON **не** подставлять как основное имя — имя всегда из фасетов. (При желании `name` можно писать в лог для сверки.)

## 6. Правила сопоставления значений фасетов

Ищем существующее значение **по тексту** `value` (не по `value_code`).

Перед сравнением нормализовать **оба** текста (из JSON и из 1С):

1. `Trim` пробелов по краям;
2. в числовых фрагментах считать **равнозначными** точку и запятую как десятичный разделитель:  
   `78.5` ≡ `78,5`.

Рекомендуемый практический приём: для сравнения временно заменить `,` → `.` в обеих строках (или наоборот) **только в контексте сопоставления**, не меняя хранимый текст при создании нового значения.

Если после нормализации совпадение найдено — использовать существующее значение, новое не создавать.  
Если нет — создать значение с **исходным** текстом из JSON (как пришло в файле).

Имена фасетов: если в категории нет реквизита с таким `name` — **всегда создавать новый**, без «умного» маппинга на похожие («Матеріал» ≠ «Материал блістера» и т.п., пока имена не совпали по правилу п. 5.1).

## 7. Порядок работ внутри позиции (кратко)

```
Для каждой позиции JSON:
  BEGIN TRAN (позиция)
    Для каждого фасета по порядку массива:
      пустой value → skip
      нет фасета в категории → создать (в конец списка)
      нет значения (с учётом 78.5 ≡ 78,5) → создать
    Собрать имя = Join(values, ", ")
    Найти ЕИ по unit (нет → пусто)
    Найти обычную номенклатуру по int_code (нет → пусто)
    Создать новый ST:
      категория, ЕИ, ссылка на номенклатуру, фасеты,
      Наименование = Полное наименование = имя
  COMMIT / при ошибке ROLLBACK позиции + лог с данными и причиной
```

Сначала по позиции закрываются фасеты/значения, **затем** создаётся ST «из» этих фасетов. Так по каждой строке JSON.

---

## 8. Что сознательно не делаем

- Не фильтруем JSON по `status` / категории из файла — грузим всё содержимое в **выбранную** в обработке категорию.
- Не ищем и не обновляем уже существующие ST (дубликаты допустимы с точки зрения обработки).
- Не создаём обычную номенклатуру.
- Не создаём единицы измерения.
- Не записываем `kmat` в реквизиты ST.
- Не подставляем готовое `name` из JSON вместо склейки фасетов.
- Не сопоставляем фасеты по `code` / значения по `value_code`.

## 9. Приёмка (чеклист)

- [ ] Выбор файла JSON и категории; вкладки «Загрузка» и «Лог».
- [ ] Отсутствующий фасет по имени появляется в категории **в конце** списка, тип — доп. значение.
- [ ] Отсутствующее значение создаётся; `78.5` и `78,5` не плодят дубль.
- [ ] Пустой `value` → фасет пропущен, в имени не участвует.
- [ ] ST создаётся всегда новый; категория = выбранная; фасеты заполнены.
- [ ] Наименование = Полное наименование = склейка через `", "` в порядке JSON.
- [ ] При валидном `int_code` заполняется поле «Номенклатура»; при отсутствии кода/элемента — ST всё равно создан, в логе пометка.
- [ ] Неизвестная ЕИ → пусто, без ошибки позиции.
- [ ] Ошибка на одной позиции откатывает только её; в логе причина + данные позиции; остальные позиции грузятся.
- [ ] Имена объектов метаданных сверены с конфигурацией (раздел 4).

## 10. Открытые уточнения для программиста 1С

1. Точные имена справочников/реквизитов и API записи фасетов в элемент ST (раздел 4).
2. Нужна ли блокировка категории на время массового создания реквизитов.
3. Ограничения длины «Наименование» / «Полное наименование» — обрезка или ошибка позиции при превышении.
4. Заполнять ли другие обязательные реквизиты ST значениями по умолчанию конфигурации (организация, вид номенклатуры и т.д., если есть).
